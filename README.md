# Бибип — файловая СУБД на Python

Учебный проект: аналог реляционной СУБД, реализованный без использования готовых
баз данных. Данные хранятся в текстовых файлах, доступ к ним организован через
собственные индексы.

Проект показывает изнутри механику, которую обычно скрывает СУБД: поиск по
индексу, последовательное сканирование, обновление записи на месте, логическое
удаление и соединение таблиц.

## Модель данных

| Таблица  | Ключ            | Содержание                          |
|----------|-----------------|-------------------------------------|
| `cars`   | `vin`           | Автомобили: модель, цена, статус     |
| `models` | `id`            | Справочник моделей и брендов        |
| `sales`  | `sales_number`  | Продажи: дата, цена, флаг отмены    |

Каждая таблица хранится в двух файлах: `<table>.txt` с данными и
`<table>_index.txt` с индексом вида `ключ → номер строки`.

## Архитектурные решения

**Записи фиксированной длины.** Каждая строка занимает ровно 501 байт (500
символов данных плюс перенос строки). Это позволяет обращаться к произвольной
записи через `seek(row_number * 501)` за одно обращение к диску, вместо
последовательного чтения файла.

**Индекс в памяти, данные на диске.** Файл индекса содержит только ключ и номер
строки, поэтому целиком помещается в оперативную память. Файлы с данными
читаются порциями по одной записи — это соответствует условию задачи о том, что
объём данных превышает доступную память.

**Бинарный поиск по индексу.** Индекс поддерживается отсортированным при каждой
операции записи, что даёт поиск за `O(log n)` вместо перебора.

**Обновление на месте.** При изменении статуса автомобиля или отмене продажи
строка перезаписывается по тому же смещению. Файл не переписывается целиком, а
номера строк остаются валидными — иначе все индексы пришлось бы перестраивать.

**Логическое удаление.** Удалить строку из файла фиксированной длины физически
нельзя: последующие записи сдвинулись бы и индексы указывали бы на мусор.
Вместо этого отменённые продажи помечаются флагом и пропускаются при чтении —
так же, как реальные СУБД не освобождают место сразу после `DELETE`.

**Смена первичного ключа.** При обновлении VIN строка данных остаётся на своём
месте, меняется только значение поля и ключ в индексе. Индекс пересортируется и
перезаписывается целиком.

## Реализованные операции

| Метод                  | Аналог в SQL                          |
|------------------------|---------------------------------------|
| `add_model`, `add_car` | `INSERT`                              |
| `sell_car`             | `INSERT` + `UPDATE` в двух таблицах   |
| `get_cars`             | `SELECT ... WHERE status = ?` (Seq Scan) |
| `get_car_info`         | `JOIN` трёх таблиц по ключу (Index Scan) |
| `update_vin`           | `UPDATE` первичного ключа             |
| `revert_sale`          | `DELETE` (логическое)                 |
| `top_models_by_sales`  | `GROUP BY` + `ORDER BY` + `LIMIT 3`   |

## Стек

Python 3.13, pydantic, pytest. Внешних зависимостей для хранения данных нет.

## Запуск

```bash
python -m venv venv
source venv/Scripts/activate      # Linux/macOS: source venv/bin/activate
pip install -r requirements.txt

export PYTHONPATH=$PYTHONPATH:$(pwd)/src
pytest tests -v
```

## Что можно улучшить

Индексы перечитываются с диска при каждом обращении. На учебном объёме данных
это незаметно, но при росте нагрузки индексы стоит держать в памяти на всё время
жизни сервиса, синхронизируя с файлом при записи.
